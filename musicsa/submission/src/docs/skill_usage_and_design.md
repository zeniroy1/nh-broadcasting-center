# 사용 스킬 및 프로그램 설계 기록

## 문서 목적

이 문서는 `musinsa-product-roadmap` 제출 구조 안에서 어떤 스킬을 사용해 프로그램을 설계하는지, 그리고 해당 스킬이 향후 구현될 프로그램에서 어떤 역할을 담당하는지 설명한다.

이 문서는 전체 대화 로그를 대체하지 않는다. 전체 대화 로그는 별도로 `logs/` 폴더에 원문 그대로 저장해야 한다.

## 1. 제작 과정에서 사용한 Codex 스킬

### plugin-creator

사용 목적:

```text
Codex 플러그인 제출 구조를 만들기 위해 사용
```

적용 내용:

```text
src/.codex-plugin/plugin.json 생성 기준 확인
src/skills/<skill-name>/SKILL.md 구조 확인
플러그인이 실제 동작 구성 요소를 가져야 한다는 조건 확인
plugin.json 필수 필드와 interface 필드 구성 확인
```

이 스킬을 사용한 이유:

```text
제출 조건이 일반 프로그램 폴더가 아니라 Codex 플러그인 구조였기 때문이다.
src 안에 플러그인 루트가 있어야 하고, src/.codex-plugin/plugin.json이 필수였으며,
plugin.json 외에 실제 구성 요소가 하나 이상 필요했다.
가장 적합한 구성 요소는 SKILL.md였기 때문에 스킬 기반 플러그인으로 설계했다.
```

## 2. 제출 플러그인이 제공하는 스킬

### musinsa-product-roadmap

위치:

```text
src/skills/musinsa-product-roadmap/SKILL.md
```

역할:

```text
무신사 공개 지표 기반 상품 탐색/파싱 프로그램을 설계하거나 검토할 때 사용하는 스킬
```

이 스킬이 다루는 핵심 문제:

```text
무신사에는 상품, 랭킹, 검색 결과, 리뷰 등 공개 자료가 많다.
하지만 사용자는 원하는 상품에 빠르게 도달하기 어렵다.
또한 정확한 구매자 수, 40대 남성 구매자 수, 랭킹 알고리즘 같은 내부 지표는 공개되지 않는다.
따라서 공개 지표를 기반으로 대체 지표를 만들고, 그 지표로 후보 상품을 비교해야 한다.
```

스킬의 주요 기능:

```text
사용자 자연어 구매 요청 해석
검색 조건 분해
공개 지표 목록 정리
내부 지표의 공개 대체 지표 설계
상품 점수화 기준 설계
추천 결과 설명 원칙 정리
MVP 범위 제한
```

## 3. 현재 플러그인에 MCP 서버를 넣지 않은 이유

현재 단계는 실제 크롤러나 파서 구현 전의 계획 단계다.

따라서 `.mcp.json`은 만들지 않았다.

이유:

```text
아직 외부 API 서버나 로컬 MCP 서버가 확정되지 않았다.
무신사 요청 방식, 요청 빈도 제한, 저장 방식, 법적/약관 검토가 남아 있다.
지금은 스킬 기반 설계 문서가 제출 조건을 충족하는 가장 안정적인 구성이다.
```

향후 코드 구현 단계에서 MCP 서버가 필요해질 수 있는 경우:

```text
무신사 공개 데이터 수집을 별도 로컬 서버로 분리할 때
상품 후보 수집/점수화/저장 기능을 도구화할 때
Codex가 직접 parser/search/recommend 함수를 호출해야 할 때
```

## 4. 향후 프로그램을 구성할 기능 모듈

실제 코드 작성 단계에서는 다음 모듈로 나누는 것이 적합하다.

### 1. Intent Parser

사용자의 자연어 요청을 구조화된 조건으로 바꾼다.

예:

```text
검은색 무지 반팔티, 2~3만원대, 40대 남성이 무난하게 입을 제품
```

변환:

```text
카테고리: 반팔 티셔츠
색상: 블랙
스타일: 무지/베이직
가격대: 20,000~39,999원
성별: 남성
연령대 힌트: 40대
```

### 2. Search Candidate Generator

하나의 요청에서 여러 검색어를 만든다.

예:

```text
검은색 무지 반팔티
블랙 무지 반팔
남성 기본 반팔티
베이직 반팔 티셔츠
무지 크루넥 티셔츠
```

### 3. Public Signal Collector

무신사 검색/랭킹/상품 상세/리뷰 영역에서 공개 지표를 수집한다.

수집 대상:

```text
상품명
브랜드
가격
할인율
리뷰 수
평점
랭킹 순위
판매 라벨
현재 구매 중/보는 중 표시
배송 정보
품절 여부
상품 상세 설명
```

현재 구현 상태:

```text
목록 수집 범위는 src/config/collection_scope.json에서 조정한다.
상품 상세 수집은 musinsa_detail_schema.py에서 필드 스키마와 수집 작업 청사진으로 정의했다.
리뷰 신호는 src/config/review_signal_keywords.json과 musinsa_review_signal_schema.py에서 보조 지표로 정의했다.
실제 네트워크 수집기는 다음 구현 단계에서 연결한다.
```

### 4. Proxy Metric Mapper

직접 알 수 없는 내부 지표를 공개 지표 기반 대체 지표로 바꾼다.

예:

```text
40대 남성 구매자 수
→ 남성/40대 랭킹 노출 여부
→ 남성 랭킹 순위
→ 리뷰 수
→ 판매 라벨
→ 평점
```

### 5. Scoring Engine

상품별 점수를 계산한다.

추천 점수 항목:

```text
목적 적합도
구매 신뢰도
리뷰 기반 구매 반응 누적 근거
남성 적합도
연령대 적합도 추정
타겟 적합도 추정
가격 적합도
배송 편의성
리뷰 리스크
```

현재 구현 상태:

```text
점수 가중치는 src/config/scoring_weights.json에서 조정한다.
musinsa_scoring_model.py가 proxy/review/public 구성 점수를 합쳐 final_score를 계산한다.
final_score는 실제 구매 전환율이나 판매량이 아니라 공개 지표 기반 추천 점수다.
리뷰 수는 구매 후 반응 누적 근거로 반영하지만 실제 구매자 수나 실제 판매량으로 단정하지 않는다.
리뷰 키워드는 타겟 적합도 추정에 반영하지만 실제 구매자 속성 통계로 단정하지 않는다.
```

### 6. Explanation Generator

추천 이유와 주의점을 설명한다.

원칙:

```text
확인 가능한 사실과 추정 결과를 분리한다.
내부 데이터를 아는 것처럼 단정하지 않는다.
사용자가 구매 판단에 바로 쓸 수 있게 짧고 명확하게 쓴다.
```

현재 구현 상태:

```text
musinsa_recommendation_output.py가 비교표, 추천 카드, 구매 판단 로드맵을 생성한다.
추천 카드에는 추천 이유, 공개 근거, 주의점을 분리해 표시한다.
출력 경계 문구에는 실제 판매 순위, 실제 구매자 수, 실제 구매자 속성 통계가 아님을 포함한다.
초기 후보 5개는 세로 막대그래프로 비교하고, 구매자가 고른 3개 후보는 세부 지표 원형/도넛 그래프 데이터로 다시 비교한다.
```

### 7. Project Audit

전체 제출 구조와 단계별 산출물의 정합성을 확인한다.

현재 구현 상태:

```text
musinsa_project_audit.py가 플러그인 구조, 단계 문서, HTML/SVG 리포트, 테스트 파일, 내부 데이터 경계, 9단계 UI 결정, 라인 수를 감사한다.
10단계 테스트는 전체 감사가 pass인지, 단계 수가 9개 구현 단계와 10개 로드맵 단계로 유지되는지, 사용자 승인 전 다음 작업 차단 정책이 있는지 확인한다.
감사 결과는 step_10_final_audit_status.html과 step_10_final_audit_status.svg로 확인한다.
```

### 8. Live Buyer App

공개 무신사 페이지 자료 수집과 구매자용 비교 UI를 연결한다.

현재 구현 상태:

```text
musinsa_live_buyer_app.py가 무신사 공개 HTML/JSON 스크립트에서 상품 후보를 파싱한다.
저장된 HTML 파일 파싱과 opt-in 라이브 fetch를 모두 지원한다.
수집 결과는 기존 intent/query/scoring/recommendation 모듈로 연결된다.
musinsa_buyer_app.html은 5개 후보 세로 막대 비교와 3개 shortlist 세부 지표를 브라우저에서 보여준다.
live_buyer_app_status.html과 live_buyer_app_status.svg는 작동 구조를 시각적으로 확인하는 산출물이다.
```

## 5. 표현 원칙

나쁜 표현:

```text
40대 남성이 가장 많이 산 상품입니다.
```

좋은 표현:

```text
남성/40대 조건의 랭킹 노출, 리뷰 수, 평점, 판매 라벨을 기준으로
40대 남성에게 적합할 가능성이 높은 상품입니다.
```

나쁜 표현:

```text
반품률이 낮은 상품입니다.
```

좋은 표현:

```text
낮은 평점 리뷰에서 사이즈/품질 불만 키워드가 적어
반품 리스크가 낮을 가능성이 있습니다.
```

## 6. 현재 단계의 결론

현재 제출물은 실제 파서 구현물이 아니라, 향후 파서/추천 도우미를 만들기 위한 Codex 플러그인 기반 설계 구조다.

현재 가장 중요한 성과:

```text
문제 정의 확정
공개 지표와 내부 지표의 경계 확정
대체 지표 설계 방향 확정
10단계 기술 구현 로드맵 작성
Codex 플러그인 제출 구조 생성
단계별 구현, 테스트, UI 리포트 생성
전체 감사 체계 생성
실사용 수집기와 구매자 UI 생성
```

다음 단계, submission.zip 재생성, Google Drive 업로드는 사용자가 명시적으로 요청할 때만 진행한다.
