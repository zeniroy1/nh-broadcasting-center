1.무엇을, 누가, 어떤 상황에서 쓰나요?
무신사 공개 데이터를 기반으로 한 상품 추천·비교 검색 도우미입니다. 
사용자가 자연어로 구매 요청을 입력하면 조건을 분해하고, 후보 상품 5개를 점수화하여 비교하며, 
그중 3개를 선별해 세부 비교까지 제공하는 로컬 웹 애플리케이션입니다.
사용 대상은 무신사에서 직접 제품을 고르려는 일반 구매자입니다. 
사이트에 처음 들어왔을 때 화면이 복잡해 무엇을 어떻게 찾아야 할지 막막한 사용자를 위한 도구입니다.
원하는 조건(색상, 가격대, 성별, 연령대, 스타일)은 비교적 분명하지만, 
무신사에서 검색·필터·랭킹·상품 상세·리뷰·브랜드 비교·가격 비교를 일일이 거치기 번거로운 상황에서 사용합니다. 
예를 들어 "검은색 반팔 무지티를 2~3만원대에서 40대 남성이 입기 좋은 제품으로 브랜드 2~3개를 추려 비교하고 싶다"와 같은 요청을, 
사용자가 직접 수행하면 오랜 탐색이 필요합니다. 이 프로그램은 그 과정을 짧게 줄이는 것을 목표로 합니다. 이는 구매자의 니즈를 어플리케이션에 적용하여
다양한 웹검색기를 만들 수 있는 가능성을 보여줍니다. 지금은 공통적인 지표를 통한 보편적접근의 검색기지만, 니즈를 파악하고 그에 맞는 지표를 생성하여
다른 의미의 검색기를 만들 수있습니다. 더 넓고 다양한 지표를 모아 지표화 시킨다면 구매자의 니즈에 맞는 다양한 웹서칭 검색기를 창조할수있음을 보여줍니다.

2.왜 이 문제를 선택했나요?
실제로 무신사를 사용하며 느낀 구체적인 불편에서 출발했습니다. 
구매자가 원하는 제품에 도달하기 어려운 구조라는 점, 랭킹의 "인기" 기준이 모호해 잘 팔려서 상위인지 노출이 많아서 상위인지 구분되지 않는다는 점, 
검색기로 목적에 맞는 제품을 찾는 과정이 직관적이지 않다는 점이 핵심 문제로 좁혀졌습니다. 그리고 적합성을 수치화 해서  구매자가 직관적으로 어느정도의 정확성있는 
제품을 빠르고 간편하게 확인할 수있도록 하는게 목표였습니다.
동시에 분명한 제약을 인정하는 데서 문제를 재정의했습니다. 실제 누적 구매자 수, 연령·성별별 구매자 수와 전환율, 반품률, 내부 랭킹 알고리즘 같은 지표는 외부에서 알 수 없습니다. 
따라서 이러한 내부 지표를 공개적으로 확인 가능한 지표로 대체하고, 공개 데이터에서 추출한 값을 토대로 신뢰도가 표기된 추정 지표를 만들어 사용자가 원하는 
제품에 도달하도록 안내하는 검색·파싱 프로그램을 만들기로 했습니다. 알 수 없는 데이터를 단정하지 않는다는 원칙이 이 문제 선택의 핵심입니다.


3.플러그인은 어떻게 작동하나요?
전체 작동 흐름은 다음과 같습니다. 자연어 입력을 받아 구매 의도를 구조화된 조건(상품군, 색상, 스타일, 가격대, 성별, 연령대)으로 파싱하고, 
여러 검색어 후보를 생성한 뒤, 무신사 공개 HTML과 JSON API에서 상품 신호를 수집합니다. 수집한 상품을 정규화하고 조건에 맞지 않는 후보와 중복을 제거한 다음, 
공개·정제·추정 지표로 점수를 계산하여 5개 후보를 비교표로 제시하고, 상위 3개를 선별해 세부 비교를 제공합니다.
작동의 핵심 특징은 다음과 같습니다. 많은 정보를 한번에 보여주는것이 아닌 처음 단계에서 정제하여 검색의 풀을 줄여나가는것입니다. 
지표를 직접 지표, 정제 지표, 추정 지표의 세 단계로 구분하며, 추정 지표에는 신뢰도를 백분율로 반드시 표기해 어느 정도의 확신을 가진 추정인지 드러냅니다. 
지금은 홈페이지에 있는 공통 데이터를 이용해서 정확성이 떨어지지만, 내부에서 구매나결제를 통해 정확한 추출데이터가 있다면 그런 지표를 통해 더욱 정확한 접근이 가능합니다.
로직을 말씀드리면, 자연어 가격 표현("2~3만원대", "3만원대" 등)을 가격 범위로 변환합니다. 나이는 전 연령대를 범위로 적용해 예컨대 23세는 20대로 매핑하며, 
데이터가 불확실한 10대는 연령 체크에서 제외하되 추후 확장 가능한 열린 구조로 둡니다.
키워드 정제 사전은 무신사 카테고리에서 실제로 사용하는 단어를 기준으로 삼아 자연어를 정확한 검색어로 대치합니다. 
색상과 제품 유형은 완전히 동일하지 않아도 유사한 값으로 매칭하며, 브랜드명이 고유명사처럼 검색되는 경우까지 포함하는 유사 검색을 지원합니다.
또한 검색기 우측에는 무신사 공개 검색어 데이터를 바탕으로 인기 검색어와 급상승 검색어를 보조 정보로 표시합니다. 
다만 이는 무신사 내부 실시간 데이터가 아니라 공개 API 또는 공개 페이지 응답이 가능한 경우에 한해 갱신되는 참고 지표입니다. 키워드를 전혀 모를 때 확인 차원에서 쓰는 보완책입니다.
응답 실패, 차단, 구조 변경이 발생하면 검색기는 해당 영역에 갱신 실패 또는 대체 안내를 표시하며, 상품 추천 점수의 핵심 산출에는 직접 반영하지 않습니다.
신규 키워드는 keyword_learning_queue.json에 pending_review 상태로 기록되고, count와 public_match_count 기준을 넘으면 promotion_ready로 표시됩니다.
바로 자동 승격되지 않고 검토 후 반영하는 구조입니다.
실행은 로컬 서버를 띄운 뒤 브라우저에서 접속하는 방식이며, 화면에서 분석을 요청하면 수집 결과가 반영됩니다.
이는 하나의 EXE 파일로 묶어서 실사용자는 EXE 파일을 더블클릭하여 바로 웹 검색기를 오픈하는 방식입니다.

4.AI를 어떻게 썼나요?
이 프로젝트 자체가 AI와의 대화를 통해 설계·구현되었습니다. 
활용 방식은 단순한 코드 생성이 아니라 문제 정의 파트너이자 단계별 구현자이며 자체 검수자로서의 역할이었습니다.
먼저 코드 작성에 앞서 문제와 제약을 충분히 토론해 목적을 확정한 뒤에야 구현 로드맵을 작성했습니다.
데이터의 범위 및 정의를 먼저하여 공통적이며,지표로활용할 수있는 데이터를 찾는 작업부터 시작하였습니다. 
구현은 단계별로 진행하되, 각 단계의 끝에 정적 검사, 구현 시뮬레이션, 불필요한 주석 정리, 코드 충돌 확인, 전체 코드 라인 정리를 포함한 자체 검수를 수행하고, 
사용자가 다음 단계 진행을 지시해야만 다음으로 넘어가는 통제된 방식을 적용했습니다. 
각 단계의 산출물은 사용자가 쉽게 확인할 수 있도록 SVG·HTML 형태의 상태 리포트로 제공했습니다. 
또한 각 질문과 요청이 최종 목적에 부합하는 정도를 백분율로 기록해, 작업이 목적에서 벗어나지 않는지 정합성을 지속적으로 추적할 수 있게 했습니다.
개발 과정에서는 다수의 코드 수정과 웹 검색, 외부 도구 호출이 반복되었으며, 
사용자 피드백으로 발견된 문제(특정 키워드 검색 실패, 링크 누락, 서버 응답 오류, 세부 지표 고정 문제 등)를 보고하고 수정하는 순환을 거쳐 완성도를 높였습니다.

5.어떻게 검증했나요?
검증은 개발 과정의 기록과 최종 재현 결과 양쪽으로 확인됩니다.
개발 과정에서는 단계마다 정적 문법 검사, 단위 테스트, 모델 검증, 서버 점검을 반복 실행했습니다. 
이는 각 단계 종료 시 자체 검수를 거친다는 원칙에 따른 것으로, 검증 명령이 작업 내내 다수 실행된 기록이 남아 있습니다. 
또한 사용자 사용 중 발견된 결함을 그때그때 보고하고 수정하는 피드백 기반 검증이 함께 이루어졌습니다.
검증에는 사람과 AI의 협업이 반드시 필요합니다. 이유는 AI는 분명 자체 검증을 할 수있습니다. 하지만, 이는 사람의 정확한 로드맵(방향성)과 판단에 의거하여 진행 가능합니다.  
로그 기록을 확인해보시면, 저는 계속 중간중간 안되는 부분을 테스트하고 AI의 대화를 무조건적으로  받아들이지 않았습니다. 
제가 사실 잘 모른다고 생각하는 분야이지만 계속적인 자기검증(예를들어 어떤지표에 대해 모른다면 그것에 대해 이해가 될때까지 질문을함)
최종 상태에서 재현한 검증 결과는 다음과 같습니다. 테스트는 모두 통과했고, 모델 검증은 오류 없이 통과했으며, 
프로젝트 자체 감사 스크립트는 전 항목을 통과했습니다. 전체 파이썬 코드의 컴파일에 문법 오류가 없었고, 플러그인 메타데이터와 설정 파일의 형식도 모두 유효했습니다. 
(이런 코딩 부분은 오히려 빠르게 자체검증을 통해 코드를 검수할 수있도록 자동화함) 기능을 확인한 후 어떤 부분이 문제인지를 다시 피드백합니다. 계속 루프형식으로 검증은 할 수있지만,
중요한건 개발자가 생각하는 의도대로 되었는지에 대한 정확한 피드백을 주지 않는다면 AI는 길을 잃고 다른 이야기를 하게됩니다. 정확히 어떤 상황인지를 인지하는것이 사람에게 중요한것 같습니다.
또한 검증단계에서는 기존에 사용하던 codex 이외의 cowork를 사용해서 교차검증을 시도했습니다. 이는 하나의 ai 에이전트를 사용하는 것보다 더 객관적으로 문제를 바라볼 수있습니다.
그리고 지속적인 사용으로인한 토큰사용에 압박문제도 있었습니다.(가장 현실적인 문제)
