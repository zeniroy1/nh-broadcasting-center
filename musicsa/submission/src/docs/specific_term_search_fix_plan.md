# 구체 품목 검색 정확도 개선 계획 (Specific-Term Search Fix Plan)

> 상태: 계획 문서 (코드 미적용). 이 문서는 "넓은 카테고리 안의 구체 품목"을 검색할 때 발생하는 정확도 문제의 원인과 수정 방안을 정리한다. 실제 코드 수정은 별도 승인 후 진행한다.

## 1. 증상

사용자가 구체 품목명을 입력해도, 그 품목이 속한 넓은 카테고리 전체로 검색이 일반화되고 형제 품목이 섞여 나온다. 동시에 검색 결과 풀이 작아진다.

재현 예시:

```text
입력: 20살 여자 래시가드 3만원 이하
결과: 비키니 등 다른 수영복 품목이 섞여 나오고 후보 수가 적음
```

확인된 동작:

```text
"여자 래시가드 3만원 이하" 생성 검색어:
  여성 수영복/비치웨어, 여성 비키니, 여성 수영복, 베이직 수영복/비치웨어 리뷰, 수영복/비치웨어

"여자 수영복 3만원 이하" 생성 검색어:
  (위와 완전히 동일)
```

즉 "래시가드"와 "수영복"이 같은 검색으로 처리되어, 구체어가 가진 변별력이 사라진다.

## 2. 영향 범위 (래시가드만의 문제가 아님)

유사어 사전과 카테고리 사전을 전수 점검한 결과, 같은 구조 문제가 여러 품목에 존재한다.

| 품목군 | 문제 | 심각도 |
|---|---|---|
| 가방 (백팩/크로스백/숄더백/메신저백) | 공통어 "가방"이 두 그룹에 들어가 그룹 병합 발생. 백팩·크로스백 입력 시 동의어가 전부 동일해짐 | 높음 |
| 모자 (비니/볼캡/캡) | 겨울 비니와 볼캡이 동의어로 묶임 | 중간 |
| 스커트 (미니스커트/롱스커트) | 길이가 정반대인 품목이 동의어로 묶임 | 중간 |
| 원피스 (미니원피스/롱원피스) | 길이가 정반대인 품목이 동의어로 묶임 | 중간 |
| 수영복 (래시가드/비키니/비치웨어) | 형태·용도가 다른 품목이 동의어로 묶임 | 중간 |
| 신발 (운동화/스니커즈 + 신발/슈즈) | 넓은 상위어 "신발/슈즈"가 구체어와 동일 그룹 | 중간 |

가방 그룹 병합 실측:

```text
백팩 입력   → backpack, bag, 가방, 메신저백, 배낭, 백팩, 숄더백, 크로스백
크로스백 입력 → backpack, bag, 가방, 메신저백, 배낭, 백팩, 숄더백, 크로스백  (동일)
```

## 3. 근본 원인 (3겹 구조)

### 3-1. 의도 파서가 구체어를 버린다
`scripts/musinsa_intent_parser.py`

구체어("래시가드")가 카테고리 키워드에 매칭되면 `product_group`(swimwear)으로 흡수되고, `free_terms`에는 남지 않는다. 그 결과 후속 검색어 생성이 구체어 대신 카테고리 라벨을 사용한다.

```text
product_group: swimwear
free_terms: []   ← "래시가드"가 사라짐
```

### 3-2. 검색어 생성이 카테고리 라벨을 그대로 쓴다
`scripts/musinsa_query_generator.py`

검색어가 `category_label`("수영복/비치웨어") 기반으로 만들어진다. 슬래시가 포함된 복합 문자열이 그대로 키워드가 되어(`keyword=수영복/비치웨어`) 무신사 검색 결과가 빈약해진다. 또한 후보에 "여성 비키니"처럼 형제 품목이 직접 포함된다.

### 3-3. 유사어 사전이 형제 품목을 동의어로 묶는다
`config/search_keyword_aliases.json` + `scripts/musinsa_live_buyer_app.py`의 `_load_keyword_aliases`

서로 다른 하위 품목이 같은 alias 그룹에 들어 있고(예: `["수영복","비치웨어","비키니","래시가드","래쉬가드","스윔웨어","swimwear"]`), 로더는 공통 단어를 공유하는 그룹들을 **하나로 병합**한다. 그래서 "가방"을 공유하는 백팩 그룹과 크로스백 그룹이 하나의 거대 그룹으로 합쳐진다.

추가로 매칭 게이트 `_matches_product_group`(`scripts/musinsa_live_buyer_app.py`)는 같은 상품군이면 전부 통과시켜 형제 품목을 거르지 못한다.

## 4. 수정 방안

### 4-1. 유사어 사전 분리 (config/search_keyword_aliases.json)

원칙: **진짜 같은 말(표기·언어 차이)만 한 그룹에 둔다. 넓은 상위어와 구체 품목은 분리한다.**

수정 예시(가방):

```text
변경 전
  ["백팩", "배낭", "가방", "backpack"]
  ["크로스백", "숄더백", "메신저백", "가방", "bag"]

변경 후 (공통어 "가방/bag" 제거로 그룹 병합 차단, 구체 품목 분리)
  ["백팩", "배낭", "backpack"]
  ["크로스백", "메신저백", "cross bag", "messenger bag"]
  ["숄더백", "shoulder bag"]
```

같은 원칙 적용 대상:

```text
모자:   ["비니", "beanie"] 와 ["볼캡", "캡", "ball cap"] 분리
스커트: ["미니스커트", "mini skirt"] 와 ["롱스커트", "long skirt"] 분리, "스커트/치마"는 상위어로 별도
원피스: ["미니원피스"] 와 ["롱원피스"] 분리
수영복: ["래시가드", "래쉬가드", "rash guard"] 와 ["비키니", "bikini"] 분리, "수영복/스윔웨어"는 상위어로 별도
신발:   ["운동화", "스니커즈", "sneakers"] 와 넓은 "신발/슈즈/shoes" 분리
```

상위어(가방, 신발, 모자, 수영복)는 별도의 "카테고리 상위어" 그룹으로 유지하되, 구체어 검색을 덮어쓰지 않게 한다.

### 4-2. 의도 파서: 구체어 보존 (scripts/musinsa_intent_parser.py)

구체어가 `product_group`으로 일반화되더라도, 원래 입력한 구체어를 별도 필드(예: `specific_terms` 또는 `free_terms`)에 **보존**한다.

```text
입력: 래시가드
변경 전 → product_group=swimwear, free_terms=[]
변경 후 → product_group=swimwear, free_terms=["래시가드"]  (또는 specific_terms=["래시가드"])
```

판단 기준: 카테고리 키워드 중에서도 "상위 카테고리어"(수영복, 가방)와 "구체 품목어"(래시가드, 크로스백)를 구분하는 표를 둔다. 구체 품목어로 입력되면 검색의 1순위 키워드로 사용한다.

### 4-3. 검색어 생성: 구체어 우선 + 슬래시 정리 (scripts/musinsa_query_generator.py)

```text
1) 구체어가 있으면 그것을 1순위 검색어로 사용한다.
   예: "여성 래시가드"  (← "여성 수영복/비치웨어"가 아니라)
2) category_label의 슬래시(/)는 분리하여 개별 검색어로 만든다.
   "수영복/비치웨어" → "수영복", "비치웨어"
3) 형제 품목(비키니 등)은 후순위 보조 검색어로만 둔다.
```

### 4-4. 매칭 게이트: 구체어 우선 정렬 (scripts/musinsa_live_buyer_app.py)

```text
1) 구체어가 지정된 경우, 상품명에 구체어가 포함된 후보를 우선(상위)으로 정렬한다.
2) 같은 product_group이지만 구체어가 없는 형제 품목은 후순위로 둔다(완전 배제는 아님 — 풀 확보).
3) _load_keyword_aliases의 그룹 병합 로직은 4-1의 사전 분리로 자연 해소되나,
   안전을 위해 "상위어는 병합 트리거로 쓰지 않음" 규칙을 추가 검토한다.
```

## 5. 검증 계획 (수정 후)

```text
1. 단위 테스트: 의도 파서에 specific_terms 보존 케이스 추가
2. 재현 테스트:
   - "래시가드" 입력 → 검색어 1순위가 "래시가드", 결과가 래시가드 중심
   - "수영복" 입력 → 수영복 카테고리 전반(래시가드·비키니 포함)
   - "백팩" 입력 → 크로스백/숄더백이 1순위에 섞이지 않음
   - "미니스커트" 입력 → 롱스커트가 1순위에 섞이지 않음
3. 회귀 테스트: 기존 116개 테스트 전부 통과 유지
4. 정적 검사: py_compile, --validate, project_audit 통과
```

## 6. 영향 및 주의

```text
- 사전 분리는 데이터(JSON) 변경이라 위험이 낮다. 우선 적용 가능.
- 파서/검색어/매칭 변경은 로직 변경이라 회귀 테스트 필수.
- 풀이 너무 좁아지지 않도록, 구체어 결과가 부족할 때 형제 품목을 보조 후보로 보충하는 fallback을 유지한다.
- 공개 지표만 사용하고 내부 데이터를 단정하지 않는 기존 원칙은 그대로 유지한다.
```
