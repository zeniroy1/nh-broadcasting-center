# 개발 논의 및 결론 도출 기록

## 문서 목적

이 문서는 무신사 상품 검색/파싱 프로그램 아이디어가 어떤 대화를 통해 구체화되었는지 기록한다.

이 문서는 제출용 전체 대화 로그가 아니다. 전체 대화 로그는 편집이나 발췌 없이 별도로 `logs/` 폴더에 저장해야 한다.

## 1. 시작점: 무신사 랭킹 페이지 파싱 가능성 확인

처음 사용자는 무신사 랭킹 URL을 전달하며 자료를 파싱할 수 있는지 질문했다.

확인한 내용:

```text
무신사 랭킹 페이지는 정적 HTML에 상품 목록이 직접 박혀 있는 구조가 아니었다.
페이지 내부에서 JSON API를 호출해 랭킹 데이터를 받아오는 구조였다.
랭킹 API 응답에는 상품명, 브랜드, 가격, 할인율, 이미지, 상품 URL, 랭킹 순위 등이 포함되어 있었다.
```

초기 결론:

```text
무신사 랭킹 데이터는 파싱 가능하다.
다만 화면 HTML보다 내부 JSON 응답을 이용하는 편이 적합하다.
```

## 2. 문제의식: 홈페이지가 복잡하고 원하는 상품을 찾기 어렵다

이후 사용자는 무신사 홈페이지가 복잡하고, 구매자가 원하는 제품을 찾기 힘든 구조가 아닌지 문제를 제기했다.

논의한 내용:

```text
무신사는 상품량과 콘텐츠가 많다.
랭킹, 추천, 세일, 발매, 카테고리, 성별, 연령대, 기간 기준이 한 화면에 섞여 있다.
사용자는 "무엇을 사야 하지?"보다 "무엇을 눌러야 하지?"를 먼저 느낄 수 있다.
```

정리된 문제:

```text
무신사는 상품 발견에는 강하지만, 목적 구매에는 복잡하다.
사용자가 원하는 조건의 상품까지 도달하려면 여러 필터와 상세 페이지를 직접 확인해야 한다.
```

## 3. 랭킹 탭의 의미 정리

사용자는 랭킹 탭이 모든 제품을 한 번에 랭킹으로 나눠 보는 것인지 질문했다.

정리한 내용:

```text
랭킹은 전체 상품을 무조건 한 줄로 세우는 것이 아니다.
상품/브랜드/검색어, 카테고리, 성별, 연령대, 실시간/급상승/누적 기준에 따라 나뉜다.
```

예시:

```text
상의 > 남성 > 40대 > 실시간 랭킹
아우터 > 전체 성별 > 전체 연령대 > 누적 랭킹
```

결론:

```text
랭킹은 조건별 인기 노출 목록으로 보는 것이 정확하다.
```

## 4. 인기 기준의 모호성 확인

사용자는 "인기"라는 기준이 너무 모호하다고 지적했다.

논의한 질문:

```text
1위 상품은 실제로 가장 많이 팔린 상품인가?
조회가 많아서 상위인가?
광고나 노출 가중치가 들어간 것인가?
급상승 기준은 무엇인가?
```

정리한 결론:

```text
무신사의 내부 랭킹 알고리즘은 공개되어 있지 않다.
따라서 랭킹 순위를 판매량이라고 단정하면 안 된다.
랭킹은 "무신사가 공개 화면에서 제공한 노출 순위"로 기록해야 한다.
```

중요한 원칙:

```text
랭킹 = 판매량순이라고 단정하지 않는다.
랭킹은 공개 지표 중 하나로만 사용한다.
```

## 5. 검색 기능의 한계 논의

사용자는 무신사에는 검색창이 있는데, 검색을 이용하면 원하는 제품을 쉽게 찾을 수 있는지 질문했다.

예시로 논의한 검색어:

```text
반팔
검은색 반팔티
무지 반팔
```

확인한 문제:

```text
검색어가 넓으면 결과가 너무 많다.
사용자는 필터와 정렬 기준을 스스로 이해해야 한다.
사용자의 목적 언어와 쇼핑몰 필터 언어가 다르다.
상품 비교 기능이 약하다.
```

결론:

```text
무신사 검색은 상품을 많이 찾는 데는 강하지만,
사용자의 상황에 맞는 하나의 상품을 고르게 도와주는 데는 복잡하다.
```

## 6. 구체 미션 설정: 검은색 무지 반팔티

사용자는 다음과 같은 구매 미션을 제시했다.

```text
검은색 반팔 무지티를 사고 싶다.
가격은 대략 2~3만원대.
브랜드는 2~3개 정도로 추리고 싶다.
40대 남성들이 많이 산 제품이면 좋겠다.
파싱 후 비교할 수 있게 조사하고 싶다.
```

이 미션에서 확인한 어려움:

```text
검은색/반팔/무지/가격대 필터링은 가능하다.
브랜드 후보 추리기도 가능하다.
리뷰 수, 평점, 판매 라벨, 랭킹 노출도 확인 가능하다.
하지만 "40대 남성이 실제로 많이 산 수치"는 공개되지 않는다.
```

일반 사용자의 예상 탐색 시간:

```text
무신사에 익숙한 사람: 15~25분
보통 사용자: 30~50분
쇼핑/필터에 익숙하지 않은 사람: 1시간 이상
```

결론:

```text
이 문제는 단순 파싱 문제가 아니라 탐색 비용을 줄이는 문제다.
```

## 7. 상품 상세 페이지까지의 파싱 가능성 확인

사용자는 결과를 도출할 수 있는 마지막 페이지, 즉 상품 상세 페이지까지 파싱이 가능한지 질문했다.

확인한 내용:

```text
상품 상세 페이지에는 초기 상품 데이터가 포함되어 있었다.
상품명, 브랜드, 상품번호, 가격, 정상가, 할인율, 이미지, 카테고리,
성별, 시즌, 배송 정보, 리뷰 수, 만족도, 상품 설명, 랭킹 기록 등을 확인할 수 있었다.
```

결론:

```text
상품 상세 페이지까지 공개 자료 파싱이 가능하다.
다만 로그인/개인화/내부 통계 데이터는 제한된다.
```

## 9. 공개 지표 기반 대체 지표 설계

사용자는 내부 지표를 공개 지표로 최대한 바꿀 수 있는지 질문했다.

정리한 대체 지표:

| 내부적으로 알고 싶은 지표 | 공개 지표 기반 대체 지표 |
|---|---|
| 실제 누적 구매자 수 | 판매 라벨, 리뷰 수, 랭킹 노출 |
| 40대 남성 구매자 수 | 남성/40대 랭킹 노출, 남성 랭킹 순위 |
| 연령대별 구매 비율 | 연령대 필터별 랭킹 순위 비교 |
| 성별별 전환율 | 남성/여성 랭킹 순위 비교 |
| 광고 노출 가중치 | AD/스폰서/기획전 표시 |
| 내부 랭킹 알고리즘 | 공개 랭킹 순위와 랭킹 기준명 |
| 개인화 추천 점수 | 비로그인 기본 추천 노출 |
| 장바구니 전환율 | 현재 구매 중, 현재 보는 중, 리뷰 수 |
| 검색 결과 노출 점수 | 검색어별 결과 순위 |
| 반품률 | 낮은 평점 리뷰와 불만 키워드 |
| 재구매율 | 리뷰 내 재구매 키워드 |

핵심 결론:

```text
내부 지표를 직접 얻으려 하지 말고,
공개 지표 기반 대체 지표를 만들어 상품 추천 근거로 사용한다.
```

## 10. 최종 목적 확정

사용자는 다음 목적을 확정했다.

```text
공개 지표에 준하는 대체 지표를 설정한다.
공개 자료에서 추출한 데이터와 대조한다.
그 데이터를 토대로 추정 지표를 만든다.
그 지표로 사용자에게 맞는 원하는 제품에 도달하도록 로드맵을 짜주는 검색 및 파싱 프로그램이 필요하다.
```

최종 프로그램 정의:

```text
무신사 공개 지표 기반 상품 검색/파싱/비교 도우미
```

핵심 기능:

```text
사용자 자연어 요청 해석
검색 조건 변환
공개 지표 수집
대체 지표 계산
상품 점수화
후보 상품 비교
추천 이유와 주의점 출력
```

최종 가치:

```text
무신사에서 직접 30~50분 걸릴 수 있는 탐색 과정을
3~5분 안에 후보 3~5개 비교로 줄인다.
```

## 12. 현재 결론

현재 단계의 결론은 다음과 같다.

```text
1. 무신사 공개 자료는 검색/랭킹/상세 페이지까지 상당 부분 파싱 가능하다.
2. 내부 구매 데이터와 랭킹 알고리즘은 공개되지 않는다.
3. 따라서 공개 지표 기반 대체 지표를 설계해야 한다.
4. 프로그램의 핵심은 단순 크롤링이 아니라 사용자의 구매 목적에 맞는 탐색 로드맵 생성이다.
5. 첫 구현은 남성 반팔 티셔츠 추천 MVP로 제한하는 것이 적합하다.
6. 현재 제출 구조는 Codex 플러그인 형태로 구성한다.
```

## 13. 목적 부합도 기록 추가

대화가 최종 목적에 맞게 진행되었는지 추후 확인할 수 있도록 별도 목적 부합도 기록표를 작성했다.

문서:

```text
src/docs/purpose_alignment_matrix.md
```

기록 방식:

```text
각 사용자 질문/요청을 최종 목적과 비교한다.
목적에 직접 기여하면 100%에 가깝게 기록한다.
보조적인 제출/파일 관리 작업은 중간 점수로 기록한다.
목적과 무관한 작업은 0%에 가깝게 기록한다.
각 점수에는 판단 이유와 도출 결과를 함께 남긴다.
```

현재까지의 종합 부합도:

```text
94%
```

종합 판단:

```text
대부분의 대화가 무신사 공개 지표 기반 상품 탐색/파싱/비교 프로그램 설계에 직접 연결되었다.
일부 폴더 위치 정리와 파일 관리 대화는 핵심 기능 설계와는 거리가 있지만,
제출 산출물 정합성에는 필요했기 때문에 낮은 점수로 처리하지 않았다.
```

## 20. 리뷰 수와 리뷰 키워드의 점수 반영

사용자는 리뷰가 구매 후 작성되는 공개 반응이므로 상품의 인기력이나 구매 경험 누적을 조사하는 지표로 사용할 수 있지 않느냐고 질문했다.

결정한 원칙:

```text
리뷰 수는 구매 후 반응 누적량의 강한 공개 단서로 사용한다.
다만 모든 구매자가 리뷰를 남기는 것은 아니므로 실제 구매자 수나 실제 판매량으로 환산하지 않는다.
리뷰 본문 키워드는 타겟 적합도를 추정하는 보조 단서로 사용한다.
리뷰 키워드 추정은 실제 연령/성별별 구매 통계가 아니므로 신뢰도 상한을 낮게 둔다.
```

추가한 지표:

```text
review_purchase_evidence_score
- 입력: 리뷰 수, 리뷰 평점, 랭킹 노출, 판매 라벨
- 의미: 구매 후 반응이 얼마나 누적되었는지 보는 공개 대체 지표
- 신뢰도 상한: 86%

buyer_context_profile_score
- 입력: 리뷰 키워드의 40대/가족/출근/재구매 타겟 단서
- 의미: 목표 구매층과 맞을 가능성을 추정하는 보조 지표
- 신뢰도 상한: 72%
```

금지 표현:

```text

리뷰 키워드에 남편이 있으므로 남성 구매자 수가 많다.
리뷰 키워드에 40대가 있으므로 40대 구매자 비율이 높다.
```

허용 표현:

```text
리뷰 수와 평점이 충분해 구매 후 반응이 누적된 상품으로 볼 수 있다.
리뷰 키워드에서 출근/남편/재구매 타겟 단서가 확인되어 타겟 적합도 추정에 반영했다.
```

## 36. 브랜드/스타일 고유 키워드의 유사 검색 허용

사용자는 `버켄스탁`처럼 공식 브랜드명인 동시에 특정 스타일을 지칭하는 키워드가 많으므로, 정확 브랜드/상품명 일치가 없더라도 무신사 검색 결과에 나온 유사 제품까지 검색기가 아우를 수 있어야 한다고 요청했다. 이에 따라 정확 매칭은 먼저 유지하되, 정확 매칭 후보가 0개일 때만 무신사 검색 API가 직접 반환한 상품을 `유사 검색 후보`로 사용할 수 있게 했다.

결정한 원칙:

```text

정확 매칭 후보가 0개일 때만 유사 검색 fallback을 켠다.
유사 검색 후보는 무신사 검색 API 출처 상품만 사용하고 랭킹 fallback 상품은 섞지 않는다.

유사 검색 후보는 final_score와 confidence_percent 상한을 둔다.
진단 패널에 `유사 검색 후보 사용`을 표시해 공식 브랜드 상품이 아닐 수 있음을 알려준다.
```

검증 예시:


## 29. 조건 미일치 fallback 차단

## 37. 무신사 공개 키워드 기반 미등록 키워드 후보 큐

사용자는 사용자가 입력한 단어가 아니라, 무신사 홈페이지에서 공개적으로 갱신되는 인기/급상승/신규 키워드 중 우리 사전에 없는 단어를 찾아 새로운 키워드 풀에 저장하는 구조가 필요하다고 정정했다. 이에 따라 검색어 트렌드 API에서 받은 공개 키워드를 기존 사전과 대조하고, 미등록 단어만 `keyword_learning_queue.json`에 누적하도록 변경했다.

결정한 원칙:

```text
새 키워드는 자동으로 category/alias 사전에 바로 편입하지 않는다.
사용자 입력 검색어가 아니라 무신사 공개 인기/급상승 키워드를 수집 대상으로 삼는다.
이미 category/color/style/gender/alias 사전에 있는 단어는 기록하지 않는다.
기록 항목은 term, normalized, count, first_seen, last_seen, sources, seen_dates, promotion_ready를 포함한다.
같은 소스에서 같은 키워드가 반복 갱신되어도 하루 1회만 count를 올린다.
동일 키워드가 3일 이상 반복 등장하면 promotion_ready로 표시한다.
승격은 사람이 검토해 alias 사전 또는 category 사전에 반영한다.
```

업데이트 주기:


## 38. 붙여 쓴 속성 표현과 만원대 가격 검색 보정

## 35. 무신사 인기/급상승 검색어 패널과 자동 갱신

사용자는 무신사 홈페이지 검색창에서 보이는 `인기 검색어`와 `급상승 검색어` 목록을 검색기 우측 영역에 넣고, 계속 실시간으로 확인할 수 있게 하고 싶다고 요청했다. 이 데이터는 구매자에게 직접 점수를 부여하는 내부 지표가 아니라, 무엇을 검색할지 모르는 상황에서 현재 많이 탐색되는 단어를 제공하는 공개 탐색 보조 지표로 사용한다.

확인한 공개 검색어 경로:

```text
주 API: https://client.musinsa.com/api/display/v1/search/web/keyword/search-home?popularCount=10&gf=A
보조 API: https://api.musinsa.com/api2/dp/v1/keyword/search-home?popularCount=10&gf=A
```

결정한 원칙:

```text
브라우저에서 직접 외부 API를 호출하지 않고 로컬 서버가 공개 API를 중계한다.
주 API가 실패하면 보조 API를 시도하고, 둘 다 실패하면 UI에 갱신 실패를 표시한다.
검색어 패널은 추천 점수에 포함하지 않고, 검색 시작을 돕는 보조 정보로만 사용한다.
인기 검색어와 급상승 검색어를 각각 10개까지 표시한다.
서버 응답 기준으로 60초마다 자동 갱신한다.
검색어를 클릭하면 입력창에 해당 단어를 넣고 현재 분석 흐름을 다시 실행한다.
```

구현 파일:


## 31. 범용 키워드 alias 기반 목적형 검색

사용자는 벨트 사례에 국한되지 않고, 모든 제품에서 단어 키워드가 목표 상품까지 이어져야 한다고 요청했다. 이에 따라 제품별 하드코딩이 아니라 공개 설정 파일 기반 alias 확장 구조로 변경했다.


## 32. PLP 상품 상세 링크 정규화

사용자는 보기 탭에 `링크 없음`이 표시된다고 지적했다. 라이브 PLP 응답을 확인한 결과 상품 상세 링크는 `goodsLinkUrl` 필드에 있었고, 기존 정규화기는 `productUrl`, `goodsUrl`, `linkUrl`, `url`, `href`만 확인하고 있었다.

```text

로컬 서버로 접속한 경우 초기 샘플의 빈 링크가 남지 않도록 첫 렌더 후 라이브 분석을 자동 실행한다.
```

## 세부 지표 재검수와 상품별 공개 신호 보정

사용자는 세부 지표의 `리스크` 값이 여러 상품에서 계속 66으로 같게 보인다고 지적했고, 이어서 `목적`, `리뷰`, `가격`, `타겟` 지표도 다시 확인해 달라고 요청했다. 검토 결과 `목적`, `리뷰`, `가격`은 공개 상품값과 사용자 조건을 직접 사용하지만, 실제 리뷰 원문을 수집하지 못한 라이브 상품의 `타겟`과 `리스크`는 샘플 리뷰 신호의 영향이 커질 수 있었다.

결정한 원칙:

```text
목적 적합도는 카테고리, 색상, 스타일, 가격, 성별 조건 일치도를 유지한다.
리뷰 지표는 공개 리뷰 수와 평점을 구매 후 반응 누적의 대체 지표로 사용한다.
가격 지표는 자연어 가격 범위와 공개 판매가 비교 결과로 산출한다.
타겟 지표는 실제 구매자 속성 통계가 아니므로 공개 랭킹, 리뷰 수, 평점, 목적 일치도 기반 대체 지표로 계산한다.
리스크는 위험 점수가 아니라 `리스크 안정성`으로 표기하고, 점수가 높을수록 공개 근거상 안정적인 후보로 해석한다.
실제 리뷰 원문이 없을 때는 공개 리뷰 수, 평점, 상품별 이슈 비율로 리스크 안정성을 계산하되 신뢰도는 낮게 제한한다.
```

구현 파일:

```text
src/scripts/musinsa_scoring_model.py
src/scripts/musinsa_live_buyer_app.py
src/tests/test_musinsa_scoring_model.py
src/tests/test_musinsa_live_buyer_app.py
```

## 실시간 인기/급상승 검색어 패널 복구

사용자는 무신사 원본 화면에는 인기 검색어와 급상승 검색어가 보이는데, 구매자 검색기 우측 패널에서는 `갱신 실패`와 `무신사 검색어를 불러오지 못했습니다`가 표시된다고 지적했다. 확인 결과 검색어 수집 자체가 아니라, 수집된 검색어를 키워드 학습 큐에 기록하는 부가 단계에서 `discovery_path=None`이 파일 경로처럼 전달되어 서버 응답이 실패하고 있었다.

결정한 원칙:

```text
실시간 검색어 표시는 핵심 UI 기능이고, 키워드 학습 큐 기록은 부가 기능이다.
학습 큐 기록 경로가 없거나 기록 중 오류가 나도 인기/급상승 검색어 패널은 유지한다.
오류는 payload.errors에 남기고 keyword_discovery.error에 기록하되, trends 데이터는 그대로 반환한다.
명시 경로가 없을 때는 keyword learning 모듈의 기본 큐 경로를 사용한다.
```

구현 파일:

```text
src/scripts/musinsa_buyer_server.py
src/tests/test_musinsa_buyer_server.py
```

## 세부 지표 리스크 표시 반전과 검색 진단 접기 UI

사용자는 세부 지표에서 `리스크`를 그대로 사용하되 `100 - 지표점수`로 반대로 표시해 높을수록 위험한 값으로 이해되게 해 달라고 요청했다. 내부 점수 모델은 `리스크 안정성`을 높을수록 좋은 값으로 쓰고 있으므로, 최종 추천 순위 계산은 그대로 두고 구매자 화면의 세부 지표 출력 단계에서만 `리스크 = 100 - 리스크 안정성`으로 변환했다.

또한 검색 진단 영역이 화면을 크게 차지하므로 접을 수 있는 아이콘 버튼을 추가했다. 버튼은 `aria-expanded`와 title을 갱신하고, 접힘 상태에서는 진단 상세만 숨긴다.

결정한 원칙:

```text
내부 추천 점수 계산은 안정성 점수를 유지한다.
구매자에게 보이는 세부 지표의 리스크만 높을수록 위험한 값으로 표시한다.
검색 진단은 필요할 때 펼쳐 볼 수 있게 하고, 기본 정보 구조는 유지한다.
```

구현 파일:

```text
src/scripts/musinsa_recommendation_output.py
src/app/musinsa_buyer_app.html
src/tests/test_musinsa_recommendation_output.py
src/tests/test_musinsa_buyer_server.py
```
